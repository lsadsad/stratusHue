## Where we are

The v2 questionnaire is ready for your review. It has 38 questions across 6 sections, with baseline answers pre-filled from firsthand template experience. Your job is to confirm, correct, or add context in the Jen column.

The stratusHue overview doc explains the plugin and how audit answers feed the build.

---

## What happens after your responses

| Step | What happens | What it produces |
|---|---|---|
| **1. Collect responses** | You fill in the Jen column at your pace | Completed questionnaire |
| **2. Re-analyze** | We reconcile your input with the baseline findings — flag agreements, corrections, new constraints, and conflicts | Updated analysis with both perspectives |
| **3. Resolve open items** | 7 decisions needing sign-off (A1–A7), 7 open questions (B1–B7), 3 clarifications (C1–C3) — we work through these together | Decision log with rationale |
| **4. Team poll (maybe)** | Section 3 (Element Check) may go to the broader team if we need more signal on specific elements | Wider input on keep/rethink/drop calls |
| **5. Revised template spec** | Everything confirmed gets written into a spec — element inventory, section map, compliance rules, variant definitions | `templateSpecRevised.md` |
| **6. Finalize for build** | Spec translates into plugin requirements — what Scaffold generates, what Validate checks, what Navigate standardizes | Build-ready reference doc |

## What we need from you

1. **Questionnaire responses** — async, at your pace. Partial is fine, specifics are better than "yes."
2. **Annotation components from the library** — needed to answer B1–B3 (annotation categories, mandatory placement, component references). This is still outstanding.
3. **Variant input** — Q4 asks what deliverable types would drive template variants. This shapes whether we build one recipe or multiple.

---

## What you don't need to worry about

- **Plugin build details** — the overview doc covers enough. We handle the translation from audit to build.
- **Getting it perfect** — disagreements and corrections are the point. If a baseline answer is wrong, say so.
- **Timeline pressure** — the build waits for the audit, not the other way around. Nothing gets built without a documented answer.
